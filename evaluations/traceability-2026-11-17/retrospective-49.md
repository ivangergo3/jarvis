# Read-only traceability exercise: authority verification

This is a retrospective, not the live pilot required by #54. The feature was separately authorized and accepted before these skill changes: [ticket #49](https://github.com/ivangergo3/jarvis/issues/49), [PR #65](https://github.com/ivangergo3/jarvis/pull/65), squash commit `b400150f9ca86f94f336b1822c234fe986c3d1c4`. Current project scope comes from REQUIREMENTS.md and the [authority guide](../../docs/engineering/authority-boundaries-49.md) at that commit. Local AC1–AC6 below refer to the six ticket acceptance bullets in their original order; they introduce no new requirements.

The actual exercise was to read those accepted criteria and the implemented source/tests, map evidence, and identify gaps that a task-only checklist could obscure. The author performed it in the same conversation. No feature changes or tests were rerun. The existing [CI run](https://github.com/ivangergo3/jarvis/actions/runs/44055371933) was inspected in the preceding implementation task: 147 tests, eight authority scenarios, five isolation probes and six native UI tests. CI tested merge-ref `3b6a5602c59e3a97d8d5d7d22714e1c2da667fe6`, not the later squash commit directly. The merge-ref and accepted squash tree must match before transferring that evidence; the structural record reports the observed tree comparison. CI artifacts expire after seven days; source assertions remain reviewable, but an expired artifact is not fresh execution evidence.

| Criterion / related baseline IDs | Implemented work | Evidence and bounded conclusion |
| --- | --- | --- |
| AC1 scoped capabilities; INT-03/05 | ActionGrant/ActionProposal and dispatch checks in AuthoritySession | Positive capability and negative scope tests; host-created authority, not model-created permission. |
| AC2 hostile external content; INT-06, SEC-02 | Four synthetic text-source scenarios, immutable resource references | Observed no-op calls, private-export test and export fault probe. Runtime scope enforcement tested; model injection-resistance rate not measured. |
| AC3 identity/outcomes; INT-04/05 | Immutable ledger, approval binding, cancellation/disconnect, receipt reconciliation | Unit tests plus lost-ack scenario; one dispatch despite repeated execution. Durable restart recovery remains a future live-integration gate. |
| AC4 isolation/logs; INT-07, SEC-01/02/03 | Isolated harness, scrubbed environment, bounded metadata | Five OS probes and audit tests. Verification sandbox only; shipping-app sandbox, Keychain isolation and hostile native-plugin containment are not established. |
| AC5 synthetic/no-op scope | Fake tool and synthetic private fixture | Harness source and observed-call evidence; no live coordinator is connected. |
| AC6 exact artifact/gaps | AuthorityGate evidence and boundary guide | Clean CI merge-ref, executable/profile hashes, call list and explicit limitations. Another model's agreement would add no runtime proof. |

The mapping exposed two review traps: a generic 'sandbox passes' checkbox could be read as shipping-app containment, and matching request IDs could be read as crash-safe deduplication. Both limitations were already documented in #49; this exercise discovered no new implementation defect. Existing unit counts alone would not explain them. It also required resolving artifact identity between CI's merge-ref and the accepted squash commit.

This table adds review context, not a new status ledger or another specification. Human review speed, avoided rework and pre-implementation gap detection were not measured. The extra cost is maintaining a source/version link and a short criterion/evidence map; avoid repeating the source guide or all test names. Use the next authorized live feature to decide whether that cost is worthwhile. Do not count this exercise as completing #54's prospective pilot criterion.
