# Queued-message recovery brief and verification plan

The proposed change should let a caller recover after losing an acknowledgement without creating a second message or presenting uncertainty as failure or success. A lost acknowledgement proves neither rejection nor acceptance. A stable client ID can correlate records, but its existence alone does not prove the server deduplicates submissions.

This brief covers the recovery behaviour, user-visible states, evidence needed to choose a safe retry policy, and proportionate verification. Existing desktop chat retains runtime ownership. This exercise authorizes planning only: no agents, messages, app changes, or test execution. Local implementation and PR preparation can follow agreement. The founder, as technical owner and test architect, decides material tradeoffs, including retry safety and acceptable unresolved-state behaviour.

## Proposed behaviour and acceptance criteria

The following are proposed requirements for agreement, not claims about existing implementation.

| ID | Scenario | Observable acceptance result |
|---|---|---|
| A1 | Acknowledgement is lost after submission | Recovery preserves the original client ID and reports an uncertain outcome until evidence establishes a narrower state. It does not automatically create a replacement message. |
| A2 | Lookup finds the same ID in the queue | The caller reconciles to the existing queued record. It reports queued/accepted as supported by that record, without claiming completed delivery. |
| A3 | Lookup finds the same ID in saved history | The caller reconciles to that existing message and reports only the status the history contract actually establishes. No duplicate is submitted. |
| A4 | Lookup finds no matching record | Absence remains inconclusive while lookup completeness and consistency are unproven. The caller does not announce definitive failure or blindly retry. |
| A5 | Lookup fails, times out, or returns conflicting evidence | Recovery preserves the message identity and unresolved state, and offers a bounded, honest recovery path. Conflicting queue/history statuses are not resolved by an invented precedence rule. |
| A6 | Recovery repeats or overlaps a late acknowledgement, restart, or another recovery attempt | The same logical message remains associated with its original identity. No additional logical message is created; statuses do not regress due to older evidence. |
| A7 | Any retry path is proposed | It is enabled only after evidence establishes safe replay semantics or authoritative nonacceptance under defined conditions. Acceptance includes the relevant race cases. |
| A8 | Integration with desktop chat | Existing runtime ownership remains intact, including lifecycle transitions. Recovery creates no competing runtime owner. |

No timeout or polling interval is agreed. The founder should select bounds after learning the consistency and rate-limit contracts. Product wording for an unresolved message and any manual recovery action also needs agreement; a retry button must not silently bypass the same safety rules.

## Risks and evidence that changes the decision

1. **Duplicate server acceptance — highest consequence.** A first request can commit while a lookup returns stale absence or a retry races it. Exposure is inherent in the stated lost-acknowledgement case; frequency is unknown. Inspect server guarantees for ID uniqueness scope, atomic deduplication, replay responses, retention/expiry, and behaviour when the same ID carries different content. A local duplicate check alone does not close this race. Duplicate acceptance may be hard to detect until both records appear; deleting a duplicate later is not a reliable rollback for downstream effects.
2. **False certainty from lookup.** Its consistency window is unspecified, and queue-to-history movement may create a visibility gap. Establish whether lookup is exhaustive and paginated, what each status means, how ordering works, and whether any documented consistency bound makes absence authoritative. Positive evidence may identify an existing message without proving final delivery.
3. **Concurrency or restart loses correlation.** Establish where the client ID and pending payload survive, what owns reconciliation, and how late responses interact with newer states. A restarted caller must not silently assign a new identity to an unresolved message. Verify through the existing runtime owner.
4. **Recovery never converges or overloads lookup.** Define a bounded lookup policy and an honest unresolved fallback using actual service limits. Repeated reads may improve visibility; they cannot prove absence without a supporting contract. Recovery should remain inspectable through ID-correlated evidence without unnecessarily recording message contents.

The material decision is whether safe replay already exists, needs a server-side contract/change, or must remain unavailable. The founder should choose after reviewing the above evidence. Pending that decision, a conservative candidate is read-only reconciliation with an explicit unresolved outcome when evidence is insufficient; it is a proposal, not an architecture commitment.

## Verification plan

Bind execution to the eventual exact commit/PR, desktop build, server/API version, and documented lookup/deduplication contracts. Use isolated synthetic messages and IDs in a local or test environment. Retain those versions, scenario timing, ID-correlated request/response traces, observed queue/history records, and UI state evidence. No checks have run for this brief.

| Criteria / risk | Planned check and data | Expected evidence |
|---|---|---|
| A1–A3; duplicate risk | Accept a synthetic submission, drop its acknowledgement, expose it first in queue and then in history; invoke recovery | One logical server message, unchanged client ID, no replacement submission, and status matching the evidence at each step |
| A4–A5; lookup uncertainty | Model stale empty reads, queue/history visibility gaps, pagination, lookup errors, and contradictory results | No false failure/success, no unsafe retry, and a preserved unresolved identity with an inspectable recovery outcome |
| A6, A8; lifecycle races | Overlap repeated recovery with late acknowledgements and queue-to-history movement; restart at each consequential boundary | No duplicate or stale state regression, identity survives as required, and desktop chat retains runtime ownership |
| A7; replay decision | Inspect the server contract and implementation; if retries are selected, exercise concurrent same-ID requests, delayed first commit, ID expiry, and payload mismatch against the actual test server | Contract-backed at-most-one logical acceptance within the agreed scope, with defined responses for every boundary |
| A1–A8; user interpretation | Founder reviews the state transitions, unresolved wording, and recovery action using scenario evidence | Clear distinction between unknown, queued, and any confirmed terminal state; explicit acceptance of remaining tradeoffs |

A deterministic local stub can validate caller transitions and race handling if an actual test server is unavailable. It cannot establish real server deduplication or lookup consistency; those remain release gaps. The implementation owner would retain check evidence; the founder chooses any additional validation depth and accepts consequential residual uncertainty. A separate QA agent is not required.

Planning is complete when this brief, criteria, evidence gaps, and decisions are reviewable. Implementation readiness requires agreement on the unresolved decisions. A later readiness claim requires mapped checks against the chosen version, evidence for the retry contract if retries are enabled, and explicit disclosure of remaining gaps. Recheck when server semantics, ID persistence, runtime lifecycle, or recovery behaviour changes. A rollback can disable new recovery/retry behaviour while preserving unresolved identities; it cannot undo messages already accepted twice.
